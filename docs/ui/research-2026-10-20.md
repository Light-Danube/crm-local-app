# UI/UX: дослідження й напрямок наступної ітерації

Дата: 20 жовтня 2026. База застосунку: main `1df7435`. Користувач підтвердив, що YouTube після останніх виправлень працює прийнятно; поточна робота не змінює його playback protocol.

Дослідження через Exa: 28 результатів у п’яти запитах, три напрями — pairing екранів, operator playback і спільний перегляд. Прочитано сім повних сторінок; відібрано шість продуктів. Відкинуто випадкові публічні кімнати з access keys, hobby-клони й старий PDF як доказ актуального вигляду UI. Це аналіз документації, а не hands-on аудит акаунтів чи рейтинг продуктів.

Висновок для нашого застосунку: **приєднання → вибір джерела → відтворення** мають бути очевидними окремими діями. Preview та головні кнопки потрібні поруч, візуальні effects — у додатковому розділі. Стан з’єднання й конкретна помилка мають з’являтися біля дії, яка їх викликала.

## Збережені приклади

[Відкрити локальну дошку схем](../../public/prototypes/references.html) або `/prototypes/references.html` на запущеному застосунку. [Машиночитний каталог](references-2026-10-20.json) містить URL, короткі цитати, дату й межі кожного прикладу.

На дошці — **власні схеми за документацією, не скриншоти продуктів**. Вони зберігаються локально й працюють без зовнішніх assets. Оригінальні UI-приклади та контекст залишаються за посиланнями першоджерел. Кольори й типографіка прототипу — наші рішення, а не результат вимірювання чужого UI.

| --- | --- | --- | --- |

| [OptiSigns](https://support.optisigns.com/hc/en-us/articles/360016374813-Set-up-add-a-screen) | Окремі кроки pair, upload, assign | Ясна послідовність і окрема дія «Передати» | Не додаємо CMS, schedules чи інтеграції з хмарними дисками |

ScreenCloud, Yodeck та OptiSigns — signage-платформи; Watch2Gether/Syncplay — спільний перегляд; ProPresenter — операторський production UI. Це суміжні сценарії, а не взаємозамінні пропозиції. Їхні заяви про синхронізацію чи надійність тут не перевірялися.

## Контрприклад і впевненість

У [Syncplay discussion #448](https://github.com/Syncplay/syncplay/discussions/448) користувач просить винести Add URL/File з меню, але maintainers пояснюють альтернативні drag/drop workflows і те, що частина налаштувань уже прихована за замовчуванням. Це одиничний діалог 2021 року, не доказ загального usability failure. Він підтримує потребу тестувати нашу ієрархію дій, а не механічно копіювати всі кнопки.

Висока впевненість: контекст коду, явний source action, preview/transport поруч і progressive disclosure підтверджуються кількома незалежними посібниками. Неперевірене: конкретна швидкість виконання завдань, реальна TV-навігація пультом і зручність нового layout для наших користувачів.

## Вимоги до інтерактивного прототипу

- Controller: блок джерела local/YouTube; явна передача; preview та play/pause/stop/seek/volume; список екранів; код і строк дії; effects у `details`.
- Display: одне поле із шістьма цифрами, без `Number()` і втрати початкового нуля; локальна перевірка перед запитом; pending, конкретна помилка й повторна спроба без закриття форми.
- Стани: немає медіа, playing/paused, offline/reconnecting, недійсний код, немає вільного місця, autoplay blocked. Текст доповнює колір.
- Мобільний layout від 320 px; видимий focus; label/error association; Enter; короткі transitions лише без reduced motion.
- Прототип використовує лише демонстраційні дані. Жодних справжніх credentials, upload, YouTube-запитів чи заяв про виміряний sync. Робочий застосунок доступний окремим посиланням.

## Порядок перенесення в робочий UI

1. Окремий статичний прототип із симуляцією станів і коротким сценарієм тестування.
2. Production pairing form замість системного prompt — без зміни server auth, TTL, rate limits чи кількості display slots.
3. Controller hierarchy: source/preview/playback перед effects. Зберегти наявні IDs та listeners, перевірити реальне декодування.
4. Допомога з адресою для іншого пристрою. Не видавати `localhost` за адресу телевізора; LAN allowlist/config лишаються явними.

Runtime/roadmap фікси продовжуються незалежними PR. UI дослідження не є підставою замінювати стек чи переписувати session/playback layer.

## Сценарії подальшого тестування

| Завдання | Критерій перевірки |
| --- | --- |
| Уперше приєднати екран | Знайти код на пульті, вставити його на display і натиснути Enter без browser prompt |
| Виправити неправильний код | Помилка біля поля, збережений ввід, зрозумілий наступний крок; відсутність зайвого server request для локально невалідного вводу |
| Передати local/YouTube й поставити на паузу | Джерело, дія передачі та playback зрозумілі; effects не заважають основному сценарію |
| Підключити другий екран | Той самий чинний код, новий identity, правильні count/slots |
| Втратити мережу або отримати autoplay denial | Видимий стан і дія відновлення; жодних stale offline commands |

Успішність, час, помилки й зауваження користувачів записувати окремо. Ця таблиця задає перевірки, не результати user study.
